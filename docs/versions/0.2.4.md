# NestGen CLI 0.2.4

Ce guide décrit le contrat prévu pour `nestgen-cli@0.2.4`.

## Installation et compatibilité

Utilisez Node.js `>=24.15.0 <27`, npm 11, pnpm 10 ou Yarn Berry 4. macOS et Linux sont pris en charge ; Windows est couvert via WSL2 car `init` appelle Bash.

```bash
npm install --global nestgen-cli@0.2.4
nestgen --version
nestgen doctor
```

## Commandes et automatisation

```text
nestgen init [name]
nestgen module <name> [--orm typeorm|prisma] [--application name] [--dry-run]
nestgen resource <name> --fields field:type[,field:type] [--route route] [--table table]
nestgen config init|show
nestgen check [--json]
nestgen doctor
```

`init --no-interactive` requiert un chemin, un package manager, l’ORM, Docker, Swagger, le socle d’exploitation, Git et `--modules`. `--json` rend les résultats et erreurs scriptables ; `--dry-run` calcule un plan sans écrire ; `--application` sélectionne une application d’un workspace Nest.

Les définitions de ressources à la version `1` acceptent champs, relations, index, filtres, recherche, tri et curseur. Les champs acceptés sont `string`, `number`, `integer`, `decimal(precision;scale)`, `enum(VALUE|VALUE)`, `boolean`, `date` et `uuid` ; `?` rend un champ nullable et `!` unique.

## Vérification des générations

Depuis la racine d’un projet généré, `nestgen check` compare les fichiers enregistrés dans `.nestgen/generation-manifest.json` à leurs empreintes. La commande ne modifie aucun fichier. Elle retourne `0` si tous les fichiers concordent et `1` si un fichier est modifié ou absent. Avec `--json`, le résultat contient `checkedFiles`, `missing` et `modified`, ainsi que `ok` dans l’enveloppe versionnée.

Les fichiers partagés, comme `src/app.module.ts`, sont vérifiés une seule fois. Une nouvelle génération actualise leur empreinte dans toutes les entrées concernées. Les anciens manifestes qui contiennent plusieurs empreintes historiques pour un même fichier restent vérifiables. Ce contrôle ne valide ni le comportement de l’application ni les migrations de base de données.

## Persistance et évolution sûre

TypeORM 0.3 et Prisma 6 sont supportés. Les relations exigent que la ressource cible existe déjà avec le même ORM. `resource --update` compare les empreintes de `.nestgen/generation-manifest.json` et bloque les fichiers modifiés manuellement. Ajoutez `--migration-name` à une mise à jour pour obtenir une commande officielle et une revue de risques ; NestGen ne crée ni n’applique une migration sans revue explicite.

## Profils, opérations et autorisation

Le profil `simple` produit un CRUD Nest direct. Le profil `advanced` ajoute contrats applicatifs, port de repository et service indépendant de Nest. `--operations` ajoute explicitement santé, logs structurés, identifiant de requête et arrêt propre sans service tiers. Chaque route de ressource porte `@ResourceAction(...)` pour les guards existants ; aucun fournisseur d’identité ni guard global n’est imposé.

## Migration depuis 0.2.3

La configuration du projet et les définitions de ressources ne changent pas. Générez une nouvelle ressource ou mettez à jour une ressource existante pour synchroniser les empreintes des fichiers partagés dans le manifeste. La commande `check` accepte aussi les manifestes antérieurs à cette synchronisation.

L'[exemple Store API](../../examples/store-api/README.md) reconstruit clients, produits, commandes et lignes de commande avec `nestgen-cli@0.2.4`, puis couvre migrations, tests et documentation.

## Limites

La CI couvre Node 24/25/26, Linux/macOS, Docker, Prisma, TypeORM/PostgreSQL et le tarball npm ; elle ne couvre pas Windows natif. Les migrations, décisions d’autorisation, déploiements et intégrations de supervision externe restent sous le contrôle explicite de l’application.
